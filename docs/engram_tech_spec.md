# ENGRAM - Technical Specification
**Version:** 1.0 - MVP | **Author:** Guna | **Date:** April 2026
**Stack:** Next.js / Supabase / OpenAI | **Related:** Engram PRD v1.0

---

## 1. Overview

Engram is a single Next.js application deployed on Vercel. No separate backend - all server-side logic lives in Next.js API routes. Data layer is Supabase (Postgres + pgvector). External services are OpenAI Embeddings API and OpenAI Chat API.

**Scope:** Text capture, vector embedding, semantic retrieval, LLM-synthesized query responses.
**Out of scope for v1:** Voice capture, external URL ingestion, authentication, React Native mobile app.

## 2. System Architecture

```
                    ENGRAM - SYSTEM ARCHITECTURE

  [Browser / PWA (Next.js + shadcn/ui)]
         |                    |
   Capture input         Query input
         |                    |
         v                    v
  +-----------------------------------------+
  |        Next.js API Routes (Vercel)       |
  |                                         |
  |  POST /api/entries    POST /api/query   |
  |         |                    |          |
  +-----------------------------------------+
            |                    |
            v                    v
  [OpenAI Embeddings API - text-embedding-3-small]
    embed content            embed question
    -> float[1536]           -> float[1536]
            |                    |
            v                    v
  +-----------------------------------------+
  |    Supabase (Postgres + pgvector)        |
  |                                         |
  |  INSERT entry +         cosine_sim       |
  |  embedding              search           |
  |                         top 5 entries   |
  +-----------------------------------------+
                               |
                               v
                  [OpenAI Chat API - GPT-4o-mini]
                  system prompt + entries context
                  -> synthesized answer + sources
```

### Capture flow
1. User types an entry and hits Enter
2. Browser POSTs `{ content }` to `/api/entries`
3. API validates content (non-empty, min 10 chars)
4. API calls OpenAI text-embedding-3-small with the content
5. OpenAI returns float[1536] vector
6. API inserts `{ content, embedding, created_at }` into Supabase
7. API returns the created entry to the browser
8. Browser appends entry to the list view

### Query flow
1. User types a question and hits Enter
2. Browser POSTs `{ question }` to `/api/query`
3. API embeds the question via OpenAI (same model, same dimensions)
4. API runs pgvector cosine similarity search against all stored embeddings
5. Top 5 most similar entries retrieved
6. API builds prompt: system instructions + question + retrieved entries
7. API calls GPT-4o-mini with the prompt
8. GPT-4o-mini returns synthesized answer citing relevant entries
9. API returns `{ answer, sources: Entry[] }` to the browser
10. Browser renders answer with source entries shown below

## 3. Data Model

```sql
-- Enable pgvector extension (run once in Supabase SQL editor)
create extension if not exists vector;

-- Main entries table
create table entries (
  id          uuid primary key default gen_random_uuid(),
  content     text not null,
  embedding   vector(1536),         -- OpenAI text-embedding-3-small dimensions
  created_at  timestamptz not null default now(),
  user_id     text                  -- null in v1, reserved for auth in v2
);

-- Index for fast approximate nearest-neighbor search
create index on entries
  using ivfflat (embedding vector_cosine_ops)
  with (lists = 100);
```

### Field notes
- **id** - UUID, generated by Postgres. Not sequential to avoid enumeration.
- **content** - raw text, no max length at DB level. App enforces soft minimum of 10 chars.
- **embedding** - 1536 floats. Must match model dimensions exactly. Model change requires full re-embedding.
- **created_at** - UTC timestamp. Used for time-filtered queries when that feature is added.
- **user_id** - nullable string for now. When auth is added in v2, becomes foreign key and Supabase RLS policies are enabled.

## 4. API Design

### POST /api/entries
- **Request:** `{ content: string }`
- **Process:** Validate -> embed via OpenAI -> insert into Supabase
- **Response:** `{ id, content, created_at }`
- **Errors:** 400 empty content, 400 content < 10 chars, 500 embedding failure, 500 DB write failure

### POST /api/query
- **Request:** `{ question: string }`
- **Process:** Embed question -> cosine similarity search -> GPT-4o-mini synthesis
- **Response:** `{ answer: string, sources: Entry[] }`
- **Errors:** 400 empty question, 500 embedding failure, 200 with no-match message if nothing found

### GET /api/entries
- **Request:** none
- **Response:** `Entry[]` ordered by created_at desc
- **Errors:** 500 DB read failure

### DELETE /api/entries/[id]
- **Request:** none
- **Response:** `{ success: true }`
- **Errors:** 404 entry not found, 500 DB failure

### Error handling principle
Every API route must handle three failure modes explicitly: invalid input (400), external service failure (500 with specific message), not found (404 for delete). Never return 200 with an error buried in the response body.

## 5. Embedding and Retrieval Pipeline

### Embedding helper
```typescript
// lib/embeddings.ts
import OpenAI from 'openai';

const openai = new OpenAI({ apiKey: process.env.OPENAI_API_KEY });

export async function embed(text: string): Promise<number[]> {
  const response = await openai.embeddings.create({
    model: 'text-embedding-3-small',
    input: text.trim(),
  });
  return response.data[0].embedding; // float[1536]
}
```

### Supabase similarity search function
```sql
-- Run in Supabase SQL editor alongside the schema
-- Called from API route via supabase.rpc('match_entries', { ... })

create or replace function match_entries(
  query_embedding  vector(1536),
  match_count      int default 5
)
returns table (
  id          uuid,
  content     text,
  created_at  timestamptz,
  similarity  float
)
language sql stable
as $$
  select
    id,
    content,
    created_at,
    1 - (embedding <=> query_embedding) as similarity
  from entries
  order by embedding <=> query_embedding
  limit match_count;
$$;
```

### Why cosine similarity
- **Dot product** - faster but not normalized. Longer entries score higher regardless of relevance.
- **Euclidean distance** - measures absolute distance, less appropriate for semantic text similarity.
- **Cosine similarity** - measures angle between vectors. Short and long entries compared fairly. Standard for semantic text search.

## 6. LLM Synthesis

### System prompt
```
You are a personal memory assistant for a specific user.
Your only job is to answer their questions based on entries they have
captured in their memory store.

Rules:
1. Answer only from the provided entries. Do not infer or make up
   information not explicitly in the entries.
2. If no entries are relevant, respond exactly with:
   "I did not find anything relevant in your captures.
    Try adding more context or rephrasing your question."
3. Be direct and concise. Do not repeat entry content verbatim
   unless quoting is essential.
4. Reference which entries you drew from, using their dates:
   e.g. "Based on your entry from April 15..."
5. If multiple entries are relevant, synthesize across them.
   Do not list them - give a unified answer.
```

### User message structure
```typescript
const formattedEntries = retrievedEntries
  .map(e => `[${formatDate(e.created_at)}]: ${e.content}`)
  .join('\n\n');

const userMessage = `
Question: ${userQuestion}

Relevant entries from my memory:
${formattedEntries}
`;
```

### Why show source entries in the UI
The LLM answer is a synthesis - users cannot verify it without seeing what it was synthesized from. Source entries build trust and let users catch retrieval errors. Transparency is a product feature, not a debug tool.

## 8. Technical Decisions Log

| Decision | Options Considered | Choice | Reasoning |
|---|---|---|---|
| Vector DB | Supabase pgvector, Pinecone, Chroma | Supabase pgvector | One service for relational + vector. Free tier sufficient at personal scale. pgvector performs well under 10k entries. |
| Embedding model | text-embedding-ada-002, text-embedding-3-small, text-embedding-3-large | text-embedding-3-small | Better than ada-002 at 5x lower cost. 1536 dimensions. Personal use costs < $0.01/month. |
| LLM synthesis | GPT-4o-mini, GPT-4o, Claude Haiku | GPT-4o-mini | 100x cheaper than GPT-4o, 3x faster. Sufficient for factual personal context synthesis. |
| Backend | Next.js API routes, FastAPI, Express | Next.js API routes | Single repo, single Vercel deploy. No CORS complexity. Right call for solo weekend build. |
| Mobile | PWA, React Native, Native iOS/Android | PWA | Same codebase as web. Installable on home screen. No App Store. 90% of native UX at 10% of build cost. |
| Authentication | NextAuth/Clerk/Supabase Auth, No auth | No auth for v1 | Significant complexity for a personal proof-of-work tool. user_id reserved in schema for v2. |
| Embedding side | Client-side, Server-side | Server-side | OpenAI API key must never be in client bundle. Non-negotiable security decision. |
| Edit entries | Allow edit + re-embed, Immutable entries | Immutable (delete + recapture) | Edit adds UX complexity and stale embedding risk. Delete-recapture handles corrections cleanly in v1. |

## 10. Security Notes

- **API keys are server-side only.** OPENAI_API_KEY and SUPABASE_SERVICE_ROLE_KEY must never appear in client code or be prefixed with NEXT_PUBLIC_.
- **Supabase RLS is disabled in v1.** Will be enabled in v2 when auth is added. Acceptable for single-user personal tool.
- **No rate limiting in v1.** Add Vercel Edge middleware or Upstash Rate Limit in v2 if URL is shared widely.
- **Input validation is minimal.** Content validated for length only. No XSS risk as content is rendered as text, not innerHTML.
